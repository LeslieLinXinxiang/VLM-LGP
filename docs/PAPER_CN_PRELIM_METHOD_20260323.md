# 中文逐字稿：Preliminaries + Method

## Title

面向长时域机器人装配的视觉-语言几何规划

## Keywords

机器人装配，逻辑-几何规划，视觉-语言模型，基于图的任务分解，任务与运动规划

## Preliminaries and Problem Statement

我们将目标装配表示为一个物体支撑图 $\mathcal{G}=(\mathcal{V},\mathcal{E})$，其中每个节点
$v \in \mathcal{V}$ 表示一个目标物体实例，每条有向边 $(u,v) \in \mathcal{E}$ 表示在最终
装配结构中，物体 $u$ 必须支撑物体 $v$。该图之所以是有向的，是因为支撑先后关系具有非对称
性：如果 $(u,v)\in\mathcal{E}$，那么物体 $u$ 必须先被实现，物体 $v$ 才能够稳定地放置。
可选的边属性，例如支撑界面上的左/右放置标签，仅被保留为局部几何提示，但它们本身并不决定
batch 序列。

规划目标是将 $\mathcal{G}$ 转换为一个有序的、面向求解器的 batch 序列
$\mathcal{B}=(B_1,\ldots,B_T)$，要求每个物体恰好出现一次，每个 batch 都保持在当前求解器
可处理的规模之内，并且对于任意出现在 $B_t$ 中的节点，其所有支撑前驱都已经在更早的 batch
中出现。换句话说，系统必须产生一种既满足结构有效性、又适合下游几何求解的分解方式。

如果将原生 LGP 直接暴露给整个完整图，会带来两个实际瓶颈。首先，长时域装配会造成过多的
符号分支，因为求解器必须在几何不可行性真正剪枝之前，先考虑大量候选的符号配置。其次，像桥
接类这样的混合支撑结构会使符号-几何搜索更加复杂，因为局部支撑关系的变化可能影响同一个全
时域问题中的较远部分。这些问题说明，在图提取与原生 LGP 实例化之间，需要插入一个分解阶段。

## Method

长时域机器人装配既需要针对目标结构的结构推理，也需要针对可执行运动的几何推理。因此，修订
后的 VLM-LGP pipeline 将支撑图作为 VLM 推理与求解器实例化之间的结构接口。整个流程包含五
个步骤：场景 grounding、支撑图构建、基于 branch 的 cutting、基于 layer 的 cutting，以及
选择性的原生 LGP 求解。其核心思想是，先把目标结构转换成关系图，再将这张图分解成少量对求
解器友好的子任务，而不是一开始就把完整的长时域任务整体暴露给原生 LGP。

### Scene Grounding and Feasibility Screening

在进行结构规划之前，系统首先将初始场景转换为一个 grounded object inventory，其中记录每个
物体的类别、几何签名以及以机器人为中心的身份信息。在同一个 grounding 阶段，系统还会通过
按物体到机器人基座的欧氏距离对同类物体进行排序，构建一个确定性的 scene-order dictionary。
这个 dictionary 仅从初始场景计算一次，随后在求解器侧的实例化过程中重复使用，用于将通用物
体请求绑定到场景中的具体实例。因此，它独立于目标支撑图，也并不定义装配策略本身。

为了在长时域规划之前排除不可行候选，系统将 waypoint 级别的 LGP 子问题作为一种低成本的可
行性测试。对于每个候选物体 $o_i$，系统会在固定时间预算 $T_{max}$ 内，在碰撞约束下求解一
个稀疏的 pick-waypoint 问题：

$$
\mathrm{Reach}(o_i)=
\mathbb{I}\!\left[
\exists\, q^* \ \text{s.t.}\ \mathrm{KOMO}_{\mathrm{wp}}(o_i, q^*)
\ \text{is feasible}
\right]
$$

能够找到可行 waypoint 的物体会被保留在 grounded inventory 中，而失败或超时的候选则会从
后续规划中排除。通过这种方式，pipeline 在进入长时域规划时，就已经拥有了一个直接来自
waypoint 级 LGP 子问题的、与求解器一致的可行性先验，同时避免了在这一阶段承担完整符号-几
何优化的代价。

### Support Graph Construction

我们并不直接让 VLM 输出精确的物体坐标，或一长串可执行代码序列，而是让它将目标规格解析为
物体支撑图 $\mathcal{G}=(\mathcal{V},\mathcal{E})$。这一设计来自于当前 VLM 的能力边界：
它们在相对空间结构、支撑关系、以及粗粒度的左右上下组织关系上通常更可靠，但在需要输出精确
数值布局、长结构化程序、或数学上严格准确的符号结果时，稳定性会明显下降。因此，我们将目标
规格转换为关系图，从而保留 VLM 更擅长提供的那部分信息。

在这张图中，每个节点表示一个目标物体实例，每条有向边表示在装配结构中必须成立的一条直接支
撑关系。支撑图是整个 pipeline 的核心接口。在上游，它将 VLM 的关系理解转换为显式的结构表
示；在下游，它为分解模块提供输入，以构造与原生 LGP 一致的子问题。图中展示了由 VLM 从目
标规格中解析得到的代表性支撑图。

### Branch-Based Cutting

一旦任务图已经得到，从求解速度、整体效率以及实际硬件限制的角度看，直接将完整图暴露给原生
LGP 并不是理想选择。因此，我们引入了一种两层 clustering 策略，把完整任务分解成更小的可执
行子任务。第一层是 branch-based cutting，其目标是在生成细粒度执行 batch 之前，先识别几个
较大的结构 branch。

在这一阶段，属于同一主支撑链的节点会被归入同一个 branch；而那些连接多个 branch 的节点，
则标志着向上层 bridge-like 结构的过渡。这一步的目的，是保留装配结构的主要组织方式，而不
是一开始就把整张图压平成一个单一的拓扑顺序。在本稿所使用的代表性支撑图中，branch-based
步骤识别出了三个粗粒度 group：左侧 branch 为 $134$，右侧 branch 为 $256$，上层 chain 为
$789$。这个结果仍然只是一个中间结构分解，而不是最终执行顺序。

### Layer-Based Cutting

在 branch-based cutting 之后，每个 branch 还会通过第二层机制进一步分解，也就是
layer-based cutting。这个阶段负责将每个较大的 branch 转换成真正面向求解器的子任务序列。
在每个 branch 内部，节点按照从低支撑层到高支撑层的顺序被扫描，并在保持前驱约束的条件下切
分成可执行的 batch。

之所以需要第二层 cutting，是因为一个 branch 对求解器来说仍然过大，不能作为单个整体任务直
接送入求解器。在当前系统中，综合考虑 LGP 的求解速度和实际硬件限制，每个可执行 batch 最多
只允许包含两个 placement 子任务。因此，这种分解不仅保留了目标图的 branch 结构，也能够匹
配下游求解器实际可高效处理的规模。

在运行示例中，layer-based cutting 将这些粗粒度 branch 进一步转换为局部序列：
$134 \mapsto 1 \mid 34$、$256 \mapsto 2 \mid 56$、$789 \mapsto 7 \mid 8 \mid 9$。
随后，再对这些局部结果执行满足 precedence 的排序，就得到最终的全局执行序列
$1 \mid 34 \mid 2 \mid 56 \mid 7 \mid 8 \mid 9$。与先前单阶段的基于规则方案相比，这种
两层分解更容易解释，因为系统先识别较大的结构 branch，再将其细化为较小的可执行 batch。

### Selective Native LGP Instantiation and Solving

原生 LGP 通过对谓词、动作语义与决策规则的统一表示，将符号任务结构与连续轨迹优化耦合起来。
原则上，这种抽象可以仅从符号目标出发求解装配任务。然而，在长时域场景中，如果直接暴露完整
的通用任务域，依然会导致过多的符号分支与不必要的几何回溯。

因此，我们的求解器只会针对每个执行 batch 选择性地实例化原生 LGP 抽象。一旦某个 batch 已
经由上述两层分解过程确定下来，系统就会读取在 scene grounding 阶段生成的 scene-order
dictionary，将通用物体类别绑定到具体的场景实例上，并且只编译当前支撑模式所需要的符号关系、
对象绑定和决策规则。这样，求解器接收到的是一个针对当前 batch 定制的 grounded 符号-几何子
问题，而不是一个覆盖所有可能装配备选项的单体域。

同一个 waypoint 级求解还会为下游的运动优化提供几何线索。设 $x$ 表示在下游阶段优化得到的
完整运动轨迹，$d_{ij}(x)$ 表示沿轨迹 $x$ 上机器人连杆 $l_i$ 与物体 $o_j$ 的最小成对距离，
$l_i^w$ 表示连杆 $l_i$ 在 waypoint $w$ 处的位姿。下游轨迹通过求解

$$
x^*=\arg\min_x J(x)
$$

并满足仅针对 active set 实例化的碰撞约束而得到：

$$
c_{ij}(x)=d_{\mathrm{safe}}-d_{ij}(x)\leq 0,\quad \forall (l_i,o_j)\in \mathcal{C}_{\mathrm{active}}(w)
$$

其中

$$
\mathcal{C}_{\mathrm{active}}(w)=
\left\{(l_i,o_j)\ \middle|\ d(l_i^w,o_j)<r_{\mathrm{active}}\right\}
$$

这里，$J(x)$ 表示下游运动目标函数，$d_{\mathrm{safe}}$ 是给定的安全裕度，$r_{\mathrm{active}}$
是根据 waypoint 几何信息筛选候选碰撞对时使用的激活半径。只有被
$\mathcal{C}_{\mathrm{active}}(w)$ 选中的对象对，才会在下游完整运动求解中被实例化为显式碰
撞约束。该 active-constraint 策略在不改变结构规划本身的前提下，减少了不必要的碰撞检查，并
缩短了完整运动求解时间。

这种受限实例化保留了原生 LGP 的表达能力，同时将搜索集中在任务中结构上相关的那一部分。它
也为图级分解与几何求解之间提供了清晰接口：分解模块决定接下来应该实现哪些支撑关系，而原生
LGP 则负责判断这些关系在当前场景几何条件下是否可执行，以及应当如何执行。

### Robot Execution

在每个子问题求解完成之后，得到的轨迹会被解析并发送给机器人控制器执行。执行层被有意保持得
很薄：它读取规划得到的运动与夹爪指令，在真实平台上执行它们，并为下一轮规划-求解循环更新
场景状态。
